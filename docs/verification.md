## 改修前の本体を読み取り確認

稼働中の1.0.3で `/api/status?logs=0` を16回取得し、応答は42〜212ms、計測カウンターは約200回/秒でした。両系統ともADC 4095、校正電圧表示3150mV、推定抵抗値 `null`、判定は `未押下` でした。本体の設定は330Ω・3300mV・mV判定で、キー送信はOFFでした。改修版の書き込みと車両スイッチの押下試験は未実施です。

測定専用APIを含むビルドが稼働している本体へ、既存LANのIPアドレスから約24秒間で52回状態を問い合わせました。全応答が接続中で、接続試行1回、失敗理由0、RSSIは−59〜−57dBmでした。応答は52〜268msで、観測中に切断は再現しませんでした。専用APIへの取得要求を3.2秒空けた試行でも、計測カウンターは200回/秒で、直近96点（最初と最後の時刻差2375ms）の電圧履歴を取得できました。

BLEの調査では、ペアリング1件、接続済み、暗号化済みのまま、キーボードとメディアキー両方が準備中でした。サービス再確認と自動再接続は各1回消費済みで、前回の切断コードはESP32側からの切断を示す `0x216` でした。ペアリングを保持した手動再接続の検証では、リンクは1秒以内、暗号化は約31秒後に成立しました。その時点でも両方のキー通知は準備中でした。

両側の登録を解除して再ペアリングした後、既存LANから約32秒間に状態25回、測定値100回を取得できました。観測中は暗号化と両方のキー通知が使用可能で、Wi-Fi切断記録とBLE自動再接続は0回でした。応答は状態37〜198ms、測定値29〜263msで、この観測では「本体との通信待ち」を再現できませんでした。

Web通信の修正版をUSBで書き込んだ後、状態13回と測定値87回の全要求が成功しました。応答は状態39〜254ms、測定値28〜293msでした。HTTP要求を送らずに開いた確認用の接続はPC側の観測で819ms後に閉じられ、`httpIdleTimeouts` が1増えました。再起動後もペアリング1件は保存され、Wi-Fi切断記録は0回でした。この再起動ではBLEの暗号化手順のタイムアウト `0x0D` とキー通知の準備待ちが再発しました。

## BLE再起動時の通知復元

診断ビルドで、再起動後、保存鍵の取得は842ms、コントローラーの暗号化成功は887ms、キーボードとメディアキーの通知復元は888msでした。その後1008msにNimBLEの `onConnect` が呼ばれ、旧ファームウェアは通知状態を初期化して、1010msに Security Request (`0x0B`) を送信していました。その要求に続くセキュリティメッセージの受信は記録されず、31010msに要求応答待ちでタイムアウトしました。

修正後は切断時に接続ごとの状態を初期化し、`onConnect` より先に復元された通知状態を保持します。すでに暗号化されている接続は暗号化要求を省きます。修正版の診断ビルドで3回再起動し、すべてで先に復元された通知を引き継ぎ、iPadのペアリング1件を保持したまま操作可能になりました。

通常ビルドをUSBで書き込んだ後、書き込みを伴わない再起動を2回行いました。起動からそれぞれ998ms、1013msで両方のキー通知が使用可能になりました。2回目は操作可能になってから35秒間、状態を45回取得し、暗号化エラー・追加の再試行は0回でした。確認時のキー送信設定はOFFでした。

再調査には `pio run -e esp32dev-ble-trace` で診断ビルドを作り、`GET /api/ble/trace` を取得します。記録は起動後の直近64件で、時刻、手順、パケット種別、結果コードを含みます。
